PART 1 — HOW THE WHOLE SYSTEM WORKS (CONCEPT)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

When a user sends a chat message, it travels through a 7-step pipeline.
Each step is a gate: if it succeeds, the pipeline stops early and returns fast.
Only if every gate fails does the request reach the expensive Gemini API.

────────────────────────────────────────────────────────────────────────────────
PIPELINE OVERVIEW  (POST /ask  →  chatbot.py → chatbot_service.py)
────────────────────────────────────────────────────────────────────────────────

  User Question
       │
       ▼
  [Weather Redirect?]  ─── YES ──→  Return "Go to Weather tab" (instant)
       │ NO
       ▼
  STEP 1 ─ CACHE CHECK  (cache/cache_engine.py)
       │  Exact/fuzzy text match in memory (in-memory list + disk JSON)
       │  Hit  ──→  Return cached answer immediately  (0 API calls, free!)
       │ Miss
       ▼
  STEP 2 ─ CROP JSON CONTEXT  (chatbot_service.py → crops/*.json)
       │  Loads relevant crop knowledge from JSON files
       │  Scores topics by keyword overlap with the question
       │  Returns top 10 topics as plain text
       │
       ▼
  STEP 3 ─ RAG RETRIEVAL  (rag/retriever.py → ChromaDB)
       │  Runs in a thread (ChromaDB is synchronous)
       │  Embeds the question with multilingual-e5-small model
       │  Searches ChromaDB vector database for top 4 similar chunks
       │  Only returns chunks with similarity score ≥ 0.55
       │  Result: 0–4 text chunks of agriculture knowledge
       │
       ▼
  STEP 4 ─ CONTEXT MERGE
       │  Combines RAG chunks + crop JSON into one context block
       │  RAG first (more specific), crop JSON second
       │
       ▼
  STEP 5 ─ CONVERSATION HISTORY  (from PostgreSQL DB)
       │  If user_id is provided: fetches last 6 messages from DB
       │  Formats as "USER: ... ASSISTANT: ..." text block
       │
       ▼
  STEP 6 ─ PROMPT BUILD  (chatbot_service.py → build_prompt())
       │  Assembles final prompt with:
       │    - Role: "You are KrashiMitra, farming assistant for UP farmers"
       │    - Language instruction (Hindi / English / Kannada)
       │    - Knowledge base (RAG chunks + crop JSON)
       │    - Conversation history
       │    - The actual question
       │  Max 5 lines output. Strict retrieval-only rules.
       │
       ▼
  STEP 7 ─ AI CALL  (chatbot_service.py → call_ai())
       │
       ├──► call_gemini()  ← tries up to 3 API keys in order
       │    │  Key 1 (GEMINI_API_KEY) → POST to Google Gemini API
       │    │    429 quota exceeded?  → try Key 2
       │    │    timeout (15s)?       → try Key 2
       │    │    success?             → return answer
       │    │  Key 2 (GEMINI_API_KEY2/GEMINI_API_KEY_2) → same
       │    │  Key 3 (GEMINI_API_KEY3/GEMINI_API_KEY_3) → same
       │    │  All failed?            → raise exception
       │    │
       │    ▼  is_good_answer()?  (not empty, not error message, ≥ 20 chars)
       │       YES → return ("answer", "gemini")
       │       NO  → fall through to Ollama
       │
       └──► call_ollama()  ← ONLY if OLLAMA_ENABLED=true (disabled by default)
            │  POST to local Ollama at OLLAMA_BASE_URL
            │  Model: OLLAMA_MODEL (default: "gemma4:e4b")
            │  60 second timeout
            │  Success → return ("answer", "ollama")
            │  Failed  → return (error message, "error")
       │
       ▼
  STEP 8 ─ SAVE TO DB  (PostgreSQL chat_history table)
       │  Saves both "user" and "assistant" messages
       │  Fields: user_id, crop, district, role, message, language, created_at
       │
       ▼
  STEP 9 ─ SAVE TO CACHE  (if source is "gemini" or "ollama" and answer is good)
       │  Embeds question with sentence-transformers (if semantic enabled)
       │  Saves to in-memory index + cache/cache_store.json on disk
       │
       ▼
  Return JSON response to user

CACHE ENGINE  (cache/cache_engine.py)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Storage   : in-memory Python list  +  cache/cache_store.json (disk)
Model     : intfloat/multilingual-e5-small (only if CACHE_SEMANTIC_ENABLED=true)
Default   : CACHE_SEMANTIC_ENABLED = false  (semantic search OFF by default)

Search logic (in order):
  1. Fuzzy text match using SequenceMatcher  (threshold: 0.94)
     Normalises punctuation, lowercases, deduplicates whitespace
     Exact or near-exact matches return instantly — no embedding needed
  2. If CACHE_SEMANTIC_ENABLED=true: embed question → cosine similarity search
     Threshold: 0.92  (very high, strict)

Save logic:
  - Checks for duplicate first (fuzzy + semantic)
  - Embeds and stores the question vector (only if semantic enabled)
  - Prunes by hit count when cache exceeds 1000 entries
  - Persists to JSON after every write

Admin operations available:
  GET  /admin/cache/stats   - view total entries, hits, top questions
  DELETE /admin/cache/clear  - clear all entries
  DELETE /admin/cache/delete - delete specific entry by question text
  PUT  /admin/cache/edit    - edit an answer
  POST /admin/cache/add     - manually add a Q&A pair

RAG SYSTEM  (rag/indexer.py  +  rag/retriever.py  +  ChromaDB)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

What is RAG?
  RAG = Retrieval Augmented Generation.
  Instead of asking the AI to answer from its training data (which may be wrong
  or outdated), we first retrieve relevant text from our own knowledge base and
  inject it into the prompt. The AI then answers from that injected text.

Index build (one-time, admin-triggered):
  Source 1: data/agri_knowledge.json   (pre-written agriculture knowledge)
  Source 2: uploads/*.pdf              (admin-uploaded PDFs)
  Chunker : 300 characters per chunk, 50 character overlap
  Embedder: intfloat/multilingual-e5-small via ChromaDB embedding function
  Storage : rag/chroma_db/ (persistent PersistentClient)
  Collection: "krashi_mitra_knowledge" with cosine similarity metric

Retrieval (per user request):
  1. Enrich query: if crop != "general", prefix with "{crop} farming: {query}"
  2. Embed enriched query using same model
  3. Search ChromaDB for top 4 most similar chunks
  4. Filter: skip chunks with similarity < 0.55
  5. Sort remaining by score descending
  6. Format as context block in Hindi: "नीचे दी गई कृषि जानकारी के आधार पर..."

Admin trigger: POST /admin/reindex (force re-indexes all sources)
Auto-index: Only if RAG_AUTO_INDEX_ON_ASK=true (default: false, for speed)

GEMINI API  (chatbot_service.py → call_gemini())
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Endpoint  : https://generativelanguage.googleapis.com/v1beta/models/{MODEL}:generateContent?key={KEY}
Model     : gemini-2.5-flash (default, set via GEMINI_MODEL env var)
Timeout   : 15 seconds per key (GEMINI_TIMEOUT env var)
Keys      : Up to 3 keys in priority order:
             GEMINI_API_KEY  → GEMINI_API_KEY2/GEMINI_API_KEY_2  → GEMINI_API_KEY3/GEMINI_API_KEY_3
Key rotation: If key returns 429 (quota exceeded) or times out → try next key
Config    : temperature=0.3, maxOutputTokens=500, topP=0.8

Token usage per request:
  Input tokens  = prompt length (typically 500–1500 tokens)
  Output tokens = answer (max 500 tokens, usually 100–200)
  Thinking tokens = INTERNAL REASONING (see Bug #1 below)

╔══════════════════════════════════════════════════════════════════════════════╗
║  BUG #1  [CRITICAL] — ROOT CAUSE OF GEMINI QUOTA EXHAUSTION               ║
║  gemini-2.5-flash uses hidden "thinking tokens" billed against quota       ║
╚══════════════════════════════════════════════════════════════════════════════╝

  Files   : backend/services/chatbot_service.py  line 119
            backend/ai_engine.py                 line 18

  Problem :
    The model is set to "gemini-2.5-flash". This is Google's "thinking" model.
    Before it writes a visible answer, it runs an internal chain-of-thought
    (reasoning steps). These THINKING TOKENS are:
      - Completely invisible in the API response
      - Billed against your daily/monthly token quota
      - Often 5x–50x larger than the actual output

    Example: A question like "गेहूँ में पानी कब दें?" (When to water wheat?)
      Output tokens (visible):  ~150 tokens
      Thinking tokens (hidden): ~3,000–15,000 tokens ← THIS IS WHAT DRAINS QUOTA

    With `maxOutputTokens: 500` set in generationConfig, you limit the output
    but NOT the thinking. The model can still think for thousands of tokens.

    This is why the API quota appears exhausted even when few users are chatting.
    Even 10–20 requests per day can exhaust a free-tier quota.

  Fix (choose one):

    Option A — Disable thinking entirely (stay on gemini-2.5-flash):
      In chatbot_service.py, add thinkingConfig to the payload:

        "generationConfig": {
            "temperature":     0.3,
            "maxOutputTokens": 500,
            "topP":            0.8,
            "thinkingConfig": {
                "thinkingBudget": 0    ← 0 means "no thinking tokens"
            },
        }

    Option B — Switch to a non-thinking model (RECOMMENDED):
      Change GEMINI_MODEL env var to: gemini-1.5-flash  OR  gemini-2.0-flash
      These are fast, cheap, non-thinking models suitable for farming Q&A.
      They answer in 1–3 seconds vs gemini-2.5-flash which can take 5–15s.

      In chatbot_service.py line 119:
        GEMINI_MODEL = os.getenv("GEMINI_MODEL", "gemini-1.5-flash")   ← change default


╔══════════════════════════════════════════════════════════════════════════════╗
║  BUG #2  [HIGH] — DEAD DUPLICATE AI ENGINE  (ai_engine.py + chat.py)      ║
╚══════════════════════════════════════════════════════════════════════════════╝

  Files   : backend/ai_engine.py  (entire file)
            backend/routes/chat.py (entire file)

  Problem :
    There are TWO separate, incompatible AI engine implementations:

    ACTIVE  (used by the app):   backend/services/chatbot_service.py
      - Multi-key Gemini rotation (3 keys)
      - Async via httpx
      - No system_instruction (all in user prompt)
      - Returns (answer, source) tuple

    DEAD    (never called in production):  backend/ai_engine.py
      - Single-key Gemini only (GEMINI_API_KEY at module load time)
      - Different API payload structure (uses "system_instruction" field)
      - Exception handling via `pass` (completely silent)
      - Referenced only by chat.py which is also dead

    backend/routes/chat.py:
      - Defines POST /ask and POST /reset routes
      - Is deliberately NOT registered in main.py (per comment in main.py)
      - Still imports AskRequest, AskResponse from backend/models.py at module top
      - Line 49: imports ai_engine.generate_answer inside the function body
      - This file is never executed in production, but creates confusion

  Risk :
    If someone accidentally adds `from backend.routes.chat import router` to
    main.py (easy mistake), it will register a SECOND /ask endpoint. FastAPI
    will use the FIRST registered one (chatbot.py's), so chat.py's broken
    single-key implementation would be silently ignored — or route conflicts
    will surface depending on FastAPI version.

  Fix :
    Delete both files entirely:
      DELETE: backend/ai_engine.py
      DELETE: backend/routes/chat.py

    These are not used. Their presence causes confusion about what code runs.


╔══════════════════════════════════════════════════════════════════════════════╗
║  BUG #3  [HIGH] — NO RATE LIMITING ON /ask ENDPOINT                       ║
╚══════════════════════════════════════════════════════════════════════════════╝

  File    : backend/routes/chatbot.py  line 75

  Problem :
    The POST /ask endpoint has no rate limiting. Any user, bot, or crawler can
    send hundreds of requests per minute, each consuming Gemini API tokens.
    Even a single automated script making 20 req/min would exhaust daily quota
    in minutes.

    The 50-second pipeline timeout (PIPELINE_TIMEOUT) protects against slow
    responses but does NOT protect against high request volume.

  Fix :
    Add slowapi (FastAPI rate limiter) to limit requests per IP:

      pip install slowapi

      In backend/main.py:
        from slowapi import Limiter, _rate_limit_exceeded_handler
        from slowapi.util import get_remote_address
        from slowapi.errors import RateLimitExceeded
        limiter = Limiter(key_func=get_remote_address)
        app.state.limiter = limiter
        app.add_exception_handler(RateLimitExceeded, _rate_limit_exceeded_handler)

      In backend/routes/chatbot.py:
        from backend.main import limiter    # or pass via dependency injection
        @router.post("/ask")
        @limiter.limit("10/minute")         # ← 10 requests per minute per IP
        async def ask(request: Request, body: Question, db: Session = Depends(get_db)):


╔══════════════════════════════════════════════════════════════════════════════╗
║  BUG #4  [HIGH] — GEMINI TOKENS CONSUMED BUT ANSWER SILENTLY DISCARDED    ║
╚══════════════════════════════════════════════════════════════════════════════╝

  File    : backend/services/chatbot_service.py  lines 199–215

  Problem :
    Current code in call_ai():

      try:
          answer = await call_gemini(prompt)
          if is_good_answer(answer):
              return answer, "gemini"
          print("[AI] Gemini returned bad/short answer, trying Ollama")
          # ← falls through! But Ollama is disabled!
      except Exception as e:
          print(f"[AI] Gemini failed: {e}")

      if os.getenv("OLLAMA_ENABLED", "false").lower() != "true":
          return ("error message", "error")  # ← returns error!

    If Gemini returns an answer but is_good_answer() returns False:
      1. Gemini tokens are ALREADY consumed (can't unconsume them)
      2. The answer is thrown away
      3. Ollama check: OLLAMA_ENABLED defaults to "false" → skipped
      4. User gets an error message

    What causes is_good_answer() to return False:
      - Answer shorter than 20 characters
      - Answer contains phrases like "i cannot", "as an ai", "क्षमा करें, अभी AI सेवा"
      - If the model refuses or gives a meta-answer about its limitations

    This means some requests waste Gemini quota AND return errors to users.

  Fix :
    Option A — Cache the Gemini answer anyway if it's reasonable:
      If Gemini responded (even borderline), use it rather than discarding.
      Only discard if the answer is truly an error/refusal.

    Option B — Adjust is_good_answer() to only reject actual error messages:
      Keep the answer if it's substantive even if short.

    Option C — Log discarded answers to understand the pattern:
      print(f"[AI] Discarded answer: {answer[:100]}")
      Then review logs to see what's being thrown away.


╔══════════════════════════════════════════════════════════════════════════════╗
║  BUG #5  [MEDIUM] — SEMANTIC CACHE DISABLED BY DEFAULT                    ║
╚══════════════════════════════════════════════════════════════════════════════╝

  File    : cache/cache_engine.py  line 24

  Problem :
    CACHE_SEMANTIC_ENABLED = os.getenv("CACHE_SEMANTIC_ENABLED", "false")...

    With semantic cache OFF, the cache only does fuzzy text matching (0.94
    threshold via SequenceMatcher). This means:

      "गेहूँ में कितना पानी चाहिए?" → cache MISS
      "गेहूँ को पानी कब देना चाहिए?"  → cache MISS  (different phrasing)
      "गेहूँ की सिंचाई कब करें?"       → cache MISS  (completely different words)

    All three questions ask the same thing but the cache misses all of them,
    sending each one to Gemini. With semantic search enabled, all three would
    match the same cached answer.

    This is the SECOND reason Gemini quota depletes faster than expected.
    The cache is barely effective without semantic matching.

  Fix :
    Set CACHE_SEMANTIC_ENABLED=true in your environment variables.
    The sentence-transformers model (multilingual-e5-small) is already set up
    for this — it just needs to be turned on.

    Trade-off: First request after server restart takes ~5s to load the embedding
    model into memory. All subsequent requests are fast (model stays in RAM).

    Set in .env or Render environment:
      CACHE_SEMANTIC_ENABLED=true


╔══════════════════════════════════════════════════════════════════════════════╗
║  BUG #6  [MEDIUM] — RAG QUERY ENRICHMENT USES LITERAL CROP KEY            ║
╚══════════════════════════════════════════════════════════════════════════════╝

  Files   : backend/routes/chatbot.py  line 148
            rag/retriever.py           line 39

  Problem :
    In retriever.py:
      if crop and crop.lower() not in ["general", "other", ""]:
          enriched_query = f"{crop} farming: {query}"

    The crop value comes from the Question model default: crop = "wheat_up"

    So the enriched query becomes:
      "wheat_up farming: गेहूँ में कितना पानी देना चाहिए?"

    The word "wheat_up" is a JSON filename key, not a natural language word.
    ChromaDB's knowledge base is unlikely to contain the string "wheat_up".
    This enrichment HURTS retrieval accuracy because:
      - It adds a meaningless technical key to the semantic search
      - "wheat_up farming:" shifts the embedding away from the actual question
      - Crops in the knowledge base are likely stored as "wheat", "गेहूँ", etc.

  Fix :
    Create a mapping from crop keys to natural language names:

╔══════════════════════════════════════════════════════════════════════════════╗
║  BUG #8  [MEDIUM] — DELETE /admin/cache/delete USES REQUEST BODY          ║
╚══════════════════════════════════════════════════════════════════════════════╝

  File    : backend/routes/admin.py  lines 109–125

  Problem :
    @router.delete("/cache/delete")
    async def delete_cache_entry(payload: dict, _: str = Depends(require_admin)):

    HTTP DELETE requests with a request body are non-standard (RFC 7231).
    Many HTTP clients (browsers, some REST clients, proxies) do not send a body
    with DELETE requests. The admin panel may fail to call this endpoint if the
    browser or fetch() strips the body from DELETE requests.

    Testing this with curl or Postman may work, but the admin HTML panel
    (admin/index.html) might not be able to call it correctly.

  Fix :
    Change to POST or use a query parameter:

      Option A (query param):
        @router.delete("/cache/delete")
        async def delete_cache_entry(question: str, _: str = Depends(require_admin)):

      Option B (change to POST):
        @router.post("/cache/delete")
        async def delete_cache_entry(payload: dict, _: str = Depends(require_admin)):

  The chat system is not working because:

  1. Gemini API quota is exhausted (Bug #1 is the root cause).
     The model gemini-2.5-flash generates hidden thinking tokens that consume
     quota 10–50x faster than the visible output suggests.
     Result: All 3 Gemini keys return 429 → call_ai() falls through to Ollama
     → OLLAMA_ENABLED=false → returns error message to user.

  2. The error message returned to the user is:
     "क्षमा करें, अभी AI सेवा उपलब्ध नहीं है। कृपया थोड़ी देर बाद पुनः प्रयास करें।"
     ("Sorry, AI service is unavailable. Please try again later.")

  3. The cache has CACHE_SEMANTIC_ENABLED=false, so only exact/near-exact
     repeated questions are served from cache. New questions always hit Gemini.

  SOLUTION:
    Fix Bug #1 (change model to gemini-1.5-flash) and
    Fix Bug #5 (enable semantic cache) and the chat will work normally again.
